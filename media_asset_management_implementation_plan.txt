MEDIA ASSET MANAGEMENT — PRODUCTION IMPLEMENTATION PLAN
===============================================================

Purpose
-------
Build a reusable, array-based media asset management system for a Next.js App Router + TypeScript + PostgreSQL + Drizzle + Cloudinary application.

The system must support:
- Single-file and multi-file uploads through the same service/API.
- Images, PDF, DOCX, and future media types.
- Maximum 2 MB final file size policy.
- Client-side validation before upload.
- SHA-256 based deduplication.
- Direct browser -> Cloudinary upload for new assets.
- Server-side verification and metadata persistence.
- Asset -> File separation.
- Soft deletion of old File references when a business record replaces media.
- Race-condition-safe asset creation.
- Partial success for bulk uploads: one failed item must not fail the entire batch.
- Per-item status/error reporting.
- Reusable APIs and services.
- No Base64 for normal uploads.
- Production-grade security and consistency.

IMPORTANT DESIGN PRINCIPLE
--------------------------
Do not build separate upload systems for:
1. profile image
2. gallery images
3. documents
4. PDFs
5. other attachments

Build ONE generic media pipeline that accepts an array of upload intents/items.

A single upload can internally be represented as an array of one item.

Example:
    processMediaAssets([profileImage])

Multiple:
    processMediaAssets([image1, image2, pdf1, docx1])

The business feature decides what each item is used for; the media subsystem only manages assets/files and lifecycle.

================================================================
1. CORE DATA MODEL
================================================================

Keep the existing conceptual separation:

Asset
-----
Represents the unique physical Cloudinary resource.

File
----
Represents one logical usage/reference of an Asset.

Relationship:

    File -> Asset -> Cloudinary resource

Example:

    Asset #10
      SHA256 = ABC...
      Cloudinary Public ID = media/abc...
      URL = https://...
          ↑
          |
    File #101 (profile image)
    File #102 (gallery image)
    File #103 (article image)

If the same physical file is uploaded again:
- Do NOT upload to Cloudinary.
- Reuse the existing Asset.
- Create a new File.
- Return the new File ID and Asset Cloudinary URL.

Existing schema:

assets:
- id
- cloudinaryPublicId
- cloudinaryUrl
- assetType
- mimeType
- sizeBytes
- fileHash
- createdAt

files:
- id
- assetId
- uploadedBy
- originalFileName
- description
- deletedAt
- createdAt

Recommended improvements:

assets:
- id
- cloudinaryPublicId
- cloudinaryUrl
- assetType
- mimeType
- sizeBytes
- fileHash
- status
- cloudinaryResourceType
- cloudinaryFormat
- width (nullable)
- height (nullable)
- createdAt
- updatedAt

Recommended asset status:
- pending
- ready
- failed

If adding status creates unnecessary complexity, at minimum only persist a completed Asset after Cloudinary confirms successful upload.

Files:
- id
- assetId
- uploadedBy
- originalFileName
- description
- deletedAt
- createdAt
- updatedAt

Do not physically delete an Asset merely because one File is soft-deleted.

Asset should only become a cleanup candidate when it has no active File references.

================================================================
2. DEDUPLICATION RULE
================================================================

Current unique key:

    UNIQUE(fileHash, assetType)

This is valid if assetType has semantic meaning.

If exact byte-level deduplication should be universal across all media categories, prefer:

    UNIQUE(fileHash)

However, make this decision based on business requirements.

Important:
The SHA-256 hash must be calculated from the ORIGINAL file bytes, before any client-side transformation.

If compression/transformation changes the bytes, the compressed output gets a different hash.

Recommended rule:

    original file
        ↓
    validate
        ↓
    calculate SHA-256
        ↓
    dedup lookup
        ↓
    if new -> compress/normalize image if needed
        ↓
    upload resulting file
        ↓
    persist metadata

BUT:
If the requirement is that identical original files always reuse the same Cloudinary asset, compression must be deterministic.

For image compression, two important strategies exist:

Strategy A — hash original bytes
--------------------------------
Pros:
- Exact duplicate source detection.
- Simple.

Cons:
- If two different source images compress to the same visual result, they will still be separate assets.
- Stored Cloudinary bytes differ from the hash source.

Strategy B — hash normalized/compressed output
---------------------------------------------
Pros:
- Deduplication is based on what is actually stored.

Cons:
- Browser must normalize/compress first.
- PDF/DOCX do not follow the same pipeline.

Recommended for this project:
Use original-file SHA-256 as the primary deduplication key because it is predictable and works for every supported file type.

Optionally add:
- normalizedHash
- processedSizeBytes

later if required.

================================================================
3. 2 MB SIZE POLICY
================================================================

Define one centralized constant:

MAX_MEDIA_SIZE_BYTES = 2 * 1024 * 1024

Do NOT duplicate "2MB" across components.

Client validation:
- file exists
- valid MIME/type
- valid extension where appropriate
- original size <= 2 MB

Server validation:
- repeat validation
- never trust client validation
- enforce maximum size independently

Important distinction:
"maximum 2 MB" should normally mean the final file uploaded/stored by the system is <= 2 MB.

For images, if original image is > 2 MB:
- Decide whether the system should reject it or attempt compression.

The requested behavior suggests:
1. Validate it is a valid supported image.
2. Apply lossless/near-lossless compression where possible.
3. Ensure final output <= 2 MB.
4. If it still cannot meet the limit, return an item-specific error.

Do NOT silently destroy quality just to meet 2 MB.

For PDF/DOCX:
- Do not apply image compression logic.
- If > 2 MB, reject unless a dedicated document optimization pipeline is intentionally introduced.

================================================================
4. IMAGE COMPRESSION POLICY
================================================================

Important terminology:
"Lossless" compression and "reduce file size significantly" are not always compatible.

PNG:
- Can use lossless optimization.
- File-size reduction may be limited.

JPEG:
- True lossless recompression is usually not useful for substantial size reduction.
- Re-encoding can introduce loss.

WebP:
- Can be lossless or lossy.
- Excellent for web delivery.

Recommended architecture:
- Preserve originalFileName and original MIME metadata.
- For images, normalize to a web-friendly format only if product requirements allow it.
- Use a deterministic compression policy.
- Never compress PDFs/DOCX through the image pipeline.

A robust browser-side approach can use a client image processing library if required, but the server must still enforce the final limits.

Recommended quality strategy:
- If image <= 2 MB: no compression unless normalization is required.
- If image > 2 MB: resize only if dimensions are excessive, then compress progressively.
- Stop once final output <= 2 MB.
- Never reduce dimensions below a configured minimum.
- If it cannot reach 2 MB within acceptable quality constraints, reject with:
  "Image is too large to process within the 2 MB limit."

Do not assume "lossless" can guarantee a target file size.

Potential image processing library:
- Browser-side: a maintained image compression library.
- Server-side: Sharp if server-side processing is required.

However, direct browser -> Cloudinary remains preferred for upload transport.

================================================================
5. FILE FLOW — NEW IMAGE
================================================================

Example: profile image.

STEP 1
------
User selects image.

Browser obtains:

    File

STEP 2
------
Validate:

- file type
- MIME type
- extension
- size
- image can actually be decoded
- maximum dimensions if required

Do not trust only file.name or MIME type.

STEP 3
------
If image processing is required:
- compress/normalize
- produce processed File/Blob
- ensure final size <= 2 MB

If the original is already acceptable:
- use original File.

STEP 4
------
Calculate SHA-256 from the bytes that are used for deduplication.

Recommended:
- Calculate hash from the exact upload candidate.

If the implementation uses original-byte hash:
- hash original File.

If it uses processed-byte hash:
- hash processed File.

Do not mix the two rules.

STEP 5
------
Send a request to Next.js:

POST /api/media/assets/prepare

Body concept:

{
  items: [
    {
      clientId: "local-item-1",
      fileHash: "...",
      assetType: "image",
      mimeType: "image/webp",
      sizeBytes: 184321,
      originalFileName: "profile.jpg"
    }
  ]
}

The API should:
- authenticate user
- validate payload
- check allowed media type
- check size
- query Assets by hash
- return per-item result.

Example response:

{
  items: [
    {
      clientId: "local-item-1",
      status: "EXISTS",
      fileId: 501,
      assetId: 10,
      cloudinaryUrl: "https://..."
    }
  ]
}

If Asset does not exist:

{
  clientId: "local-item-1",
  status: "UPLOAD_REQUIRED",
  upload: {
    cloudName: "...",
    apiKey: "...",
    timestamp: 1234567890,
    signature: "...",
    folder: "media"
  }
}

NEVER return Cloudinary API secret to the browser.

================================================================
6. SIGNED CLOUDINARY UPLOAD
================================================================

For production, prefer signed uploads.

Browser:
    asks Next.js for upload authorization

Next.js:
    authenticates user
    validates upload intent
    generates Cloudinary signature

Browser:
    uploads actual File directly to Cloudinary

Cloudinary:
    returns upload result

Browser:
    sends Cloudinary result to Next.js

Next.js:
    verifies result
    creates/reuses Asset
    creates File

The browser should NEVER upload the file through the Next.js server as Base64.

Cloudinary receives multipart FormData containing the File.

7. FINALIZE API
================================================================

Endpoint concept:

POST /api/media/assets/finalize

Request:

{
  items: [
    {
      clientId: "local-item-1",
      fileHash: "...",
      assetType: "image",
      originalFileName: "profile.jpg",
      mimeType: "image/webp",
      sizeBytes: 184321,
      cloudinary: {
        publicId: "...",
        secureUrl: "...",
        resourceType: "image",
        format: "webp",
        bytes: 184321,
        width: 512,
        height: 512
      }
    }
  ]
}

Server MUST:
- authenticate
- validate all fields
- validate size <= 2 MB
- validate allowed type
- verify Cloudinary response as much as practical
- never trust arbitrary publicUrl/publicId submitted by the client
- ensure the Cloudinary resource belongs to the expected upload context/folder
- re-check Asset by hash
- handle race conditions
- create Asset only when needed
- create File reference
- return File ID and Cloudinary URL.

================================================================
8. RACE CONDITION HANDLING
================================================================

Critical scenario:

Request A:
    checks hash -> no Asset

Request B:
    checks hash -> no Asset

Both upload same file.

Both attempt:

    INSERT Asset

Database unique constraint must reject one.

Therefore:
- Keep the unique DB constraint.
- Do not rely only on "SELECT then INSERT".

Recommended transaction logic:

1. Begin transaction.
2. SELECT Asset by unique key.
3. If exists:
       create File referencing it.
4. If not:
       INSERT Asset.
5. If unique conflict occurs:
       fetch existing Asset.
       create File referencing existing Asset.
6. Commit.

Important:
Do not leave a transaction holding locks while waiting for Cloudinary network upload.

Cloudinary upload should happen BEFORE the short DB transaction.

This creates a possible orphan Cloudinary object if the DB insert loses a race.

Handle this safely with cleanup.

================================================================
9. ORPHAN CLOUDINARY RESOURCE HANDLING
================================================================

Scenario:

Browser uploads to Cloudinary.
Then two clients finalize the same hash.

One wins DB Asset creation.
The other loses because Asset already exists.

The losing Cloudinary upload is now an orphan.

Solution:
- Generate deterministic or traceable public IDs.
- Mark unused uploads for cleanup.
- After detecting duplicate during finalize, enqueue/delete the losing Cloudinary resource.
- Never immediately delete a Cloudinary resource that might belong to the winning Asset.

Alternative:
Use deterministic Cloudinary public_id derived from hash.

Example:

    media/assets/{hash}

But verify Cloudinary behavior and overwrite/versioning settings carefully before implementation.

A background cleanup worker is recommended for orphan cleanup.

================================================================
10. FILE SOFT DELETE
================================================================

When a business entity replaces an image:

Old:
    File #100 -> Asset #10

New:
    File #200 -> Asset #20

Operation:

    File #100.deletedAt = now()

Then create/use File #200.

Never delete Asset #10 immediately.

Why:
Asset #10 may still be referenced by:
- another business record
- another user
- another gallery item
- another File

Asset cleanup should happen asynchronously.

================================================================
11. REPLACE MEDIA API
================================================================

Do not make every feature manually implement:

1. create new File
2. delete old File

Create a reusable service:

    replaceFileReference({
      oldFileId,
      newFileId,
      userId,
      ...
    })

Or, preferably, keep replacement inside the business transaction where the business row changes.

Example:

Transaction:

    UPDATE profile
       SET profileImageFileId = newFileId

    UPDATE files
       SET deletedAt = now()
     WHERE id = oldFileId

Both should succeed or fail together.

Important:
The media service should not blindly soft-delete a File without checking authorization/ownership.

================================================================
13. CONCURRENCY
================================================================

Do NOT use:

    Promise.all(files.map(...))

for an unbounded number of files.

Use controlled concurrency.

Example configuration:

    MEDIA_UPLOAD_CONCURRENCY = 3 or 4

Hashing and Cloudinary upload should be limited separately if needed.

Potential pipeline:

    validation
       ↓
    hashing
       ↓
    prepare API
       ↓
    existing assets -> immediate File creation
       ↓
    new assets -> controlled Cloudinary uploads
       ↓
    finalize API
       ↓
    success/error per item

The client can process 3-5 active uploads at a time.

14. SINGLE UPLOAD SUPPORT
================================================================

A profile image should use exactly the same array API.

    POST /api/profile-image

doing all media work itself,

the profile feature should call the generic media service with:

    items: [profileImage]

The profile business operation then receives:

    fileId
    cloudinaryUrl

and stores the File ID.

This keeps the media system reusable.

19. SECURITY
================================================================

Client validation is UX.

Server validation is security.

Server must validate:
- authenticated user
- authorization
- fileHash format
- MIME type
- size
- allowed assetType
- filename length
- description length
- Cloudinary upload information
- ownership of existing File before replacement/deletion

Never trust:
- client-provided URL
- client-provided publicId
- client-provided size
- client-provided MIME type

Cloudinary API secret:
- server only
- never NEXT_PUBLIC_
- never sent to browser

Use signed uploads.

Restrict Cloudinary folder/path based on application rules.

21. ERROR HANDLING
================================================================

Every media item must have its own error.

Do not return:

    "Upload failed"

for a batch.

Return:

    clientId
    error code
    user-friendly message

Example:

Image 1:
    success

Image 2:
    FILE_TOO_LARGE

Image 3:
    success

Image 4:
    UPLOAD_FAILED

The UI should be able to retry only failed items.

Never expose:
- database errors
- Cloudinary secrets
- internal stack traces

to users.

Log detailed internal errors server-side.

================================================================
22. RETRY STRATEGY
================================================================

Client should retry transient Cloudinary/network errors.

Do not blindly retry:
- invalid file
- unsupported type
- file too large
- authorization failure

Retry:
- network interruption
- temporary Cloudinary failure
- temporary 5xx response

Use limited retries with backoff.

Example:

    attempt 1
    wait 500ms
    attempt 2
    wait 1s
    attempt 3

Then mark item as failed.

26. CLEANUP WORKER
================================================================

Use a background worker for asynchronous cleanup.

Potential jobs:

media:cleanup-orphan

Example lifecycle:

      ↓
Asset still has active references?
      ↓
YES -> do nothing
      ↓
NO
      ↓

      ↓

================================================================
27. CLOUDINARY ORPHAN CLEANUP
================================================================

Possible orphan cases:
- Cloudinary upload succeeds but finalize API fails.
- Database transaction fails.
- Another request wins the deduplication race.
- User closes browser after Cloudinary upload.
- Network failure occurs after Cloudinary accepted upload.

Recommended:
- use a recognizable folder/prefix
- store upload timestamps
- optionally maintain an upload session
- periodic worker identifies resources not associated with a ready Asset
- cleanup only after a safe grace period.

Never run immediate aggressive deletion.

================================================================
28. TRANSACTION BOUNDARIES
================================================================

Do not put external Cloudinary HTTP calls inside DB transactions.

Bad:

    BEGIN
      upload Cloudinary
      INSERT Asset
      INSERT File
    COMMIT

This keeps a database transaction open during network I/O.

Better:

    validate
       ↓
    Cloudinary upload
       ↓
    short DB transaction
       ├── find Asset
       ├── create/reuse Asset
       └── create File
       ↓
    commit

If transaction loses a race:
- reuse existing Asset
- cleanup duplicate Cloudinary resource asynchronously.

30. CLIENT UPLOAD ALGORITHM
================================================================

Pseudo-flow:

function uploadMediaFiles(files):

    create upload items with clientId

    for each item:
        validate

        if invalid:
            mark error
            continue

        process image if required

        calculate SHA-256

    call prepare API for valid items

    for each prepared item:
        if EXISTING:
            mark success with returned File ID/URL

        if UPLOAD_REQUIRED:
            put into upload queue

    upload queue:
        controlled concurrency

        upload File directly to Cloudinary

        on success:
            send finalize information

        on failure:
            mark only that item failed

    return complete result array

================================================================
31. PROFILE IMAGE REPLACEMENT FLOW
================================================================

User has:

    profileImageFileId = 50

User selects new image.

Pipeline:

1. validate new image
2. compress/normalize if needed
3. calculate SHA-256
4. prepare API
5. if duplicate Asset exists:
       create new File -> existing Asset
6. otherwise:
       signed Cloudinary upload
7. finalize:
       create Asset
       create File
8. business transaction:
       update user.profileImageFileId -> new File ID
       soft-delete File #50
9. return new File ID + URL

Important:
If the new image fails at any step, File #50 must remain active.

Never soft-delete the old File before the new File is successfully created.

================================================================
32. MULTIPLE GALLERY FLOW
================================================================

For 3 images:

    [A, B, C]

A:
    existing Asset -> new File -> success

B:
    new Asset -> Cloudinary -> File -> success

C:
    invalid > 2MB -> error

Final:

    A success
    B success
    C failed

Do NOT roll back A and B just because C failed.

This is intentionally partial-success behavior.

35. HASHING
================================================================

Browser SHA-256:

    File
      ↓
    arrayBuffer()
      ↓
    crypto.subtle.digest("SHA-256", buffer)
      ↓
    hex string

No Base64 conversion is required.

For current <= 2 MB files this is reasonable.

If later supporting very large files:
- use streaming/chunked hashing
- use chunked/resumable Cloudinary upload
- avoid loading huge files fully into memory.

================================================================
36. API RESPONSE CONTRACT
================================================================

Use one consistent response structure.

Example:

{
  "items": [
    {
      "clientId": "upload-1",
      "status": "success",
      "fileId": 101,
      "assetId": 20,
      "cloudinaryUrl": "..."
    },
    {
      "clientId": "upload-2",
      "status": "error",
      "error": {
        "code": "FILE_TOO_LARGE",
        "message": "Maximum allowed file size is 2 MB."
      }
    }
  ]
}

Do not make callers interpret different response shapes for single vs multiple uploads.

A single upload simply has one item.

39. IMPORTANT EDGE CASES
================================================================

Case: same image uploaded twice
--------------------------------
Expected:
- one Asset
- two Files

Case: same file uploaded by two users
--------------------------------------
Expected:
- one Asset
- two Files
unless business policy intentionally isolates assets per tenant.

Case: user replaces image with identical image
------------------------------------------------
Can reuse the same Asset.
Create a new File if logical File history/reference matters.

Case: old File soft-deleted
----------------------------
Asset remains if another File references it.

Case: new upload fails
----------------------
Old File remains active.

Case: Cloudinary upload succeeds but DB fails
----------------------------------------------
Cleanup worker eventually removes orphan.

Case: two requests create same Asset
-------------------------------------
DB unique constraint resolves race.

Case: one item fails in a batch
--------------------------------
Other valid items continue.

Case: file is exactly 2 MB
--------------------------
Accept if policy means <= 2 MiB.

Case: file is 2 MB decimal vs binary
-------------------------------------
Define explicitly:
    2 MiB = 2 * 1024 * 1024 bytes

Use the same definition everywhere.

43. KEY RULES — DO NOT BREAK THESE
================================================================

1. No Base64 for normal uploads.
2. Browser uploads directly to Cloudinary.
3. Server owns authorization and persistence.
4. Never expose Cloudinary API secret.
5. Validate on both client and server.
6. SHA-256 is used for deduplication.
7. Keep Asset and File separate.
8. Business tables reference File IDs, not URLs.
9. Use DB unique constraints for race-condition protection.
10. Do not hold DB transactions during Cloudinary network calls.
11. Old File is soft-deleted only after new File succeeds.
12. One failed bulk item must not fail unrelated items.
13. Use controlled upload concurrency.
14. Keep errors item-specific.
15. Use a worker for orphan/unused-asset cleanup.
16. Do not blindly implement this plan; first analyze the existing project.
17. Keep the architecture generic so one item and many items use the same pipeline.
18. Never use `any` or `as any`; use explicit TypeScript types, `unknown`, schemas, and type guards where necessary.
19. Keep the implementation production-oriented but avoid unnecessary infrastructure.
20. The final implementation should follow the project's existing conventions where they are sound.
